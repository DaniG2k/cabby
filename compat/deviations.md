# Deviations from the Go reference

Cabby may improve on the Go implementation internally (algorithms, data structures,
concurrency). This file records only the changes that can be **observed from outside**
(wire format, defaults, limits, ordering, error codes, CLI output, timing contracts), plus
fixes to test tooling. Each entry links a test that pins the new behavior.

Internal changes that keep observable behavior identical don't need an entry. The
compatibility suite and the Go-vs-Rust benchmarks cover them.

| ID | Area | Go behavior | Cabby behavior | Why | Test | Status |
|---|---|---|---|---|---|---|
| D-001 | test tooling | `features/runner.rb` waits for exit before reading a child's output pipe; deadlocks when output exceeds the pipe buffer (seen with 8 KiB pipes) | `cabby_testkit::process::Supervised` drains stdout/stderr continuously | correctness of the harness; no server behavior involved | `crates/cabby-testkit/src/process.rs` | adopted |
| D-002 | test translation | `protocol_test.go` `TestNewCommandMessage/Base` asserts `NotNil("/cable-test", …)`, which is vacuous | assertion kept as written; separate regression asserts URL equality | SPEC §6 | `protocol::protocol_test::test_new_command_message::base_url_equality` | adopted |
| D-006 | test tooling (AnyT ports) | AnyT waits `sleep 1` after an unsubscribe or `stop_stream_from` (no acknowledgement in Action Cable) | the port sends a subscription to `Cabby::BarrierChannel` on the same session and waits for its confirmation; this relies on the server applying a session's commands in order (true for Go: `Session.ReadMessage` handles commands sequentially), which is a stricter contract than the sleep | deterministic and faster than a sleep; the stricter contract is pinned for Cabby | `conformance::anyt_default::many_clients_one_unsubscribes`, `conformance::anyt_default::single_stream_none_after_unsubscribe`, `conformance::anyt_default::multiple_streams_none_after_unsubscribe`, `conformance::anyt_default::stop_streams_unsubscribes_from_stream` (and their other `anyt_<target>` copies) | adopted |
| D-007 | test tooling (AnyT ports) | AnyT's remote-disconnect scenario sleeps 1 s after `welcome` (guarding an Action Cable-only race) | the port sends the remote disconnect right after `welcome`, relying on the server registering the session (with its identifiers) before sending `welcome` (true for Go: `Node.Authenticated` runs before the transmissions are sent) | the guard is not needed for AnyCable servers; the stricter contract is pinned for Cabby | `conformance::anyt_default::remote_disconnect_by_id` (and its other `anyt_<target>` copies) | adopted |

| D-014 | test tooling (`cabby_testkit::timers`) | n/a (Go tests use real `time.Ticker`s, whose channel delivers each tick to one receiver) | `ManualTicker::recv` takes the buffered tick under the same lock that observed it (`Watched::wait_and_update`); before, two receivers waking together could both take one tick, so the disconnect queue rate test saw two Disconnect calls per tick | the controlled clock must match Go ticker semantics (one tick, one receiver) | `node::disconnect_queue_test::test_disconnect_queue_run::respects_the_rate_with_multiple_workers` (failed intermittently before the fix) | adopted |
| D-003 | Redis pub/sub liveness (pub/sub subscriber and legacy Redis broadcaster) | If Redis drops the node's stream subscription (subscription gone, connection alive) or the subscriber connection goes half-open, the node never resubscribes and silently stops delivering broadcasts until restarted | The subscriber connection (RESP3) applies every `subscribe`/`unsubscribe` push to a confirmed set and keeps it equal to the set of streams with local subscribers: an unsolicited `unsubscribe` for a stream that still has subscribers is re-`SUBSCRIBE`d after 1 s; a subscription count in a push that disagrees with the confirmed set re-subscribes every stream; every 10 s the internal channel is re-subscribed to get a fresh count and differences are fixed; every 5 s a `PING` with a 5 s reply timeout checks the connection, and a dead or half-open connection is replaced (reconnect, resubscribe everything). Delivery resumes within ~1 s after a dropped subscription (bound 15 s) and ~10 s after a half-open connection (bound 30 s) | anycable/anycable#275 (open, not reproduced upstream); reproduced deterministically with `cabby_testkit::fault_proxy` | `conformance::issues::delivery_recovers_after_redis_drops_the_stream_subscription`, `conformance::issues::delivery_recovers_after_the_subscriber_connection_goes_half_open` (need the server binary), `pubsub::redis_issues_test::resubscribes_after_redis_drops_a_stream_subscription`, `pubsub::redis_issues_test::recovers_after_the_subscriber_connection_goes_half_open` (fail on Go: upstream defect) | adopted |

## Proposed (not adopted yet)

Record a proposed observable change here first, with its rationale and a test, before you implement it.

| ID | Area | Go behavior | Proposed Cabby behavior | Why | Pinning test | Go result |
|---|---|---|---|---|---|---|
| D-004 | Redis pub/sub subscription lifecycle | Pinned version releases channels after the last subscriber leaves (fixed in 1.6.8 for this pattern) | Same, as a hard invariant: no Redis subscription for a stream without local subscribers | anycable/anycable#263 (open; reporter still sees growth) | `conformance::issues::redis_pubsub_channels_are_released_when_streams_have_no_subscribers`, `pubsub::redis_issues_test::releases_channels_of_unsubscribed_streams` | passes (regression guard, no behavior change) |
| D-005 | Memory stability | Slow RSS growth under traffic over days | No unbounded growth: after repeated connect/subscribe/broadcast/disconnect churn, RSS, threads, sockets and file descriptors return to within a fixed margin of baseline | anycable/anycable#265 (open) | Planned soak workload in `crates/cabby-bench` (M7), run against both servers | to measure |
| D-008 | JSON log lines | `slog.NewJSONHandler` marshals slices of log wrappers as is: `CompactValues(...)` (unexported fields) logs as `[{},{}]` | Lists and maps are rendered from their resolved values: `["short","long...(1900)"]` | the upstream output carries no information; values were clearly intended (they are what the text handler prints) | `cabby-core` `logger::format::tests::renders_json_like_slog` | n/a (Go prints `{}` per element) |
| D-009 | Worker pool panics | A panic inside a `GoPool` task crashes the whole process | The panic is caught (and reported by the panic hook); the worker keeps serving the pool | one faulty task (e.g. a remote disconnect) should not take every connection down | `cabby-core` `utils::gopool::tests::survives_a_panicking_task` | n/a (Go process exits) |
| D-010 | Broadcast data JSON (`common.StreamMessage.ToReplyFor`) | Data decoded with `UseNumber` is re-encoded with each number's text verbatim, e.g. `1E2` stays `1E2` | Mantissa and digits are kept exactly (serde_json `arbitrary_precision`), but the exponent marker is normalized: `1E2` and `1e2` become `1e+2` | serde_json normalizes exponents while parsing; the value is the same JSON number, and only data using exponent notation is affected | `cabby-core` unit test `common::json::tests::deviation_d006_exponent_text_is_normalized` | differs (Go keeps `1E2`) |
| D-011 | JSON decoding edge cases (`common`, `encoders`) | Broadcast data nested up to 10000 levels, or containing lone UTF-16 surrogate escapes (`"\ud800"`) or invalid UTF-8, is decoded (invalid code points become U+FFFD); client and pub/sub decode errors use Go's texts (`invalid character ...`) | Such broadcast data is sent as a string (nesting limit 128, no lossy decoding); client messages with invalid UTF-8 fail to decode; decode error texts are serde_json's | serde_json limits and strictness; the nesting limit also bounds stack use on hostile input. No test or client depends on the error texts | `cabby-core` unit test `common::json::tests::deviation_d007_undecodable_data_is_sent_as_string` | differs (Go decodes the data) |
| D-012 | Configuration file parsing | BurntSushi/toml (TOML 1.0) parses the file; syntax errors read e.g. `toml: line 1 (last key "host"): expected value but found '\n' instead` | The `toml` crate (TOML 1.1, a superset: newlines and trailing commas in inline tables, `\e`, optional seconds) parses the file; syntax errors read `toml: line N: <toml crate message>`. Decoding over the parsed document (exact/case-insensitive key matching, type-mismatch and range errors with line and last key, unknown keys) reproduces BurntSushi/toml, verified byte for byte against Go. Two decode edge cases differ: settings typed narrower in Rust than Go's `int` (`api.port` u16, `broker.history_limit` usize, `ws.max_pending_size` u64, which Go wraps) reject negative or out-of-range values with `<n> is out of range for <type>`, and an `rpc.DialFun` key (an untagged Go function field) is reported as unknown instead of failing with `unsupported type` | maintained parser; reproducing BurntSushi's syntax-error wording would mean a hand-written parser | `cabby_core::toml_config::tests::syntax_errors_name_the_line` | differs on invalid TOML only |
| D-013 | Hub gate panics | A panic while a gate delivers a broadcast (e.g. in a session's `Send`) crashes the whole process | The panic is caught (and reported by the panic hook); the gate keeps delivering later broadcasts | same rationale as D-009: one faulty session should not stop broadcasts for every stream of the gate | `cabby-core` `hub::tests::deviation_d013_gate_survives_a_panicking_session` | n/a (Go process exits) |
| D-015 | Disconnect queue rate (`[disconnector] rate`) | A rate of 0 divides by zero, and a rate above 1000 makes a zero ticker period (`1000 / rate` ms); both panic when the queue is built | A rate below 1 runs at 1 call/s, a rate above 1000 at the fastest valid period (1 ms, 1000 calls/s) | a configuration value should not crash the server; valid rates (1 to 1000) are unchanged | `cabby-server` `node::disconnect_queue::tests::deviation_d015_out_of_range_rates_are_clamped` | n/a (Go panics) |
| D-016 | Node gauges `goroutines_num`, `mem_sys_bytes` | Go runtime statistics: the goroutine count and `MemStats.Sys`; with `ANYCABLE_MEMORY_METRICS=1` also heap/stack gauges | Same names and descriptions; the values are the process's OS threads and resident memory (`/proc/self/status`, 0 elsewhere); the Go-heap gauges are not registered | there is no goroutine or Go heap in Cabby; these are the closest process-level equivalents | `cabby-server` `node::app::tests::deviation_d016_process_stats_report_threads_and_resident_memory` | differs (Go reports its runtime) |
| D-017 | CLI fatal errors (`cmd/anycable-go`) | A configuration error is printed by `log.Fatalf` as `2006/01/02 15:04:05 <error>` in the local time zone, exit status 1 | Same text and status; the timestamp is UTC | avoids a time zone database dependency for one line; identical in UTC deployments (most containers) | `cabby-server` bin unit test `tests::deviation_d014_fatal_log_timestamp_is_utc` | differs outside UTC |
| D-018 | `--metrics_tags` without a value (`env` instead of `env:dev`) | `parseTags` indexes past the split result: runtime panic `index out of range [1] with length 1`, goroutine trace, exit status 2 | Panics with `invalid metrics tag "env": expected key:value`, exit status 101 | still a crash, with a message naming the bad tag | `cabby-server` `cli::options::tests::deviation_d015_malformed_metrics_tag_panics_with_a_message` | differs (message, status) |
| D-019 | CLI values for settings typed narrower in Rust | `--api_port` and `--history_limit` (and their `ANYCABLE_*` variables) accept any Go `int` | Values outside the Rust type (`u16`, `usize`) are clamped: negative to 0, too large to the type's maximum (the configuration file rejects them instead, D-012) | Go's out-of-range values are unusable anyway (a port above 65535, a negative history limit) | `cabby-server` `cli::options::tests::deviation_d016_narrow_settings_are_clamped` | differs on out-of-range values only |
| D-020 | WebSocket compression (`ws.enable_compression`) | gorilla negotiates `permessage-deflate` (no context takeover) when enabled and the client offers it | The setting is accepted (and logged as unsupported) but the extension is never negotiated; frames are sent uncompressed | neither maintained Rust WebSocket implementation considered (tungstenite, fastwebsockets) implements permessage-deflate; clients must accept an unnegotiated extension, so nothing breaks. Off by default upstream | `cabby-server` `ws::tests::deviation_d014_compression_is_not_negotiated` | differs only with `--enable_ws_compression` |
| D-021 | WebSocket framing edge cases | A text frame with invalid UTF-8 is handed to the session (decoding fails later, D-011); a close reason over 123 bytes makes the close frame invalid, so only the TCP connection is closed; data sent before the handshake response is rejected | The connection fails with close code 1007; close reasons are cut to 123 bytes (on a character boundary) and the close frame is sent; early data is buffered and read | RFC 6455 compliance (tungstenite validates text frames); the close frame carries the code clients rely on | `cabby-server` `ws::tests::deviation_d015_invalid_utf8_text_closes_with_1007`, `ws::connection::tests::cuts_close_reasons_to_fit` | differs (Go delivers the bytes) |
| D-022 | HTTP/2 over TLS | With `--ssl_cert`/`--ssl_key`, Go's server offers `h2` by ALPN and serves plain HTTP endpoints (health, broadcast, API) over HTTP/2 | ALPN offers `http/1.1` only; every endpoint is served over HTTP/1.1 (WebSockets are HTTP/1.1 in both) | one HTTP/1.1 stack keeps per-connection memory low; the endpoints are low-volume | `cabby-server` `server::tests::serves_over_tls` | differs (Go negotiates `h2`) |
| D-023 | NATS broker backlog | Broadcasts made while JetStream is still initializing (after `HandleBroadcast` waits 1 s) are added to a backlog that is only flushed when initialization *fails*, and that flush re-adds each message to the backlog under the held mutex (deadlock). After a successful initialization, the backlog is never published | The backlog is published (stored in JetStream and broadcast with epoch and offset) once JetStream is ready. It is dropped if initialization fails | the backlog exists to publish these messages; upstream loses them silently | `cabby-core` `broker::nats::tests::deviation_d020_backlog_is_published_once_jetstream_is_ready` | differs (Go never publishes them) |
| D-024 | NATS `max_reconnect_attempts = 0` | `nats.MaxReconnects(0)`: never reconnect after the connection is lost | One reconnect attempt (async-nats treats 0 as unlimited and has no "never"). Negative values stay unlimited, positive values unchanged | no equivalent in the maintained Rust client | `cabby-core` `nats::client::tests::deviation_d021_zero_max_reconnects_allows_one_attempt` | differs for 0 only |
| D-025 | NATS components used before they are ready | NATS broker `Subscribe`/`SetEpoch`/`Reset` before JetStream is initialized dereference a nil JetStream context (panic). | D-026 | Embedded NATS (`--embed_nats`) | The NATS server is linked into the binary and runs in-process | `enats::Service` runs the official `nats-server` binary (bundled next to `cabby`, `CABBY_NATS_SERVER`, or `PATH`) as a supervised child process configured from `enats.Config` (see `docs/enats.md`): a runtime dependency on a Go binary. | D-027 | Redis pub/sub protocol | rueidis speaks RESP3 and falls back to RESP2 on servers without `HELLO` (Redis < 6) | The pub/sub subscriber connections (pub/sub subscriber, legacy Redis broadcaster) use RESP3 only, so they need Redis 6 or later; command connections (publishing, streams) use RESP2 | RESP3 pushes carry subscription changes separately from replies, which the D-003 recovery relies on; Redis 5 is end-of-life | none (needs a Redis 5 server; CI runs Redis 7) | n/a (Go supports Redis 5) |
